Part 2: Core Syntax Reference

The Quantum

⧞ (T-Quantum) – the fundamental particle of TADA structure

  • Separates values: Alice⧞Bob⧞Charlie
  • Separates types from names: ⧞1⧞age
  • Creates transitions between states

One quantum = one step

The Quantonic

⧞⧞ (T-Quantization) – phase boundary between regions

Two uses:

  1. Schema → Data boundary:
.root⧞⧞name⧞⧞age⧞⧞    # schema ends
Alice⧞25               # data begins
  1. Data → End boundary:
Alice⧞25⧞⧞             # data ends, block closed

Phase shift = two quanta

Basic Structure

.<name>⧞<schema>⧞⧞<data>⧞⧞

Example:

.person⧞⧞name⧞1⧞age⧞⧞Alice⧞25⧞⧞

Breakdown:

  • .person⧞ – root name + quantum
  • ⧞name⧞1⧞age⧞⧞ – schema (name: string, age: int)
  • Alice⧞25 – data
  • ⧞⧞ – close

Type System (1-6)

Important: These numbers representing types in our list are not hardcoded by default. TADA is a dynamic data type system—type identifiers are determined by the implementation, not by the format itself.

Type as a field can contain any symbol combination without limit for length. It can include:

  • Numbers: 1, 42, 999
  • Letters (any alphabet): A, α, א, 中
  • Symbols: #, @, *, →
  • System symbols: ⧞ itself (if escaped), |, ~
  • Any combination: int32, user_defined_type, 🔢📝

Like any other field in TADA, type identifiers have no inherent restrictions.

TADA is the broth—you decide what to cook in it.

Want types as emojis? ✅
Want types as ancient Greek? ✅
Want types as mathematical symbols? ✅
Want types as single bits? ✅

The format is pure structure (⧞). Everything else is your choice.

Our convention (for this guide):

Why we use single-digit numbers: We stick with a numeric, minimalist approach to demonstrate maximum compression potential. One character per type = maximum efficiency.

This is our recipe. Yours can be completely different.

Part 3: Optimization Techniques

Overview

TADA’s basic structure is already efficient. But we can compress further using three techniques:

  1. L1 Dictionary – abbreviate repeated field names
  2. Schema Library – reuse common structures
  3. BASE36 Encoding – compress large numbers

Combined, these can reduce size by 50%+ beyond basic TADA.

L1 Dictionary: Bidirectional Compression

The Problem

Field names repeat constantly:

firstName, lastName, employeeId
firstName, lastName, employeeId
firstName, lastName, employeeId
firstName, lastName, employeeId
firstName, lastName, employeeId

In our JSON example, these three fields appear 5 times = 135 characters wasted on repetition.

The Solution

Create an abbreviation dictionary that maps short keys to full names:

fN ↔ firstName
lN ↔ lastName
eID ↔ employeeId

Structure

.L1⧞2⧞2⧞⧞
fN⧞firstName
⧞lN⧞lastName
⧞eID⧞employeeId
⧞pID⧞projectId
⧞pN⧞projectName
⧞addr⧞address
⧞cty⧞city
⧞st⧞state
⧞zip⧞zipCode
⧞ctry⧞country
⧞⧞

Format:

  • Root: .L1
  • Schema: Type 2 (string), Type 2 (string)
  • No field names needed—structure is self-describing (first = key, second = value)
  • Close with ⧞⧞

Bidirectional Mapping

L0 → L2 (DI to Human):

.L1.fN → "firstName"

L2 → L0 (Human to DI):

.L1.firstName → "fN"

Important: DI doesn’t “parse” or “lookup”—it sees the graph structure directly. For DI, .L1.fN is a node that connects to “firstName” instantly, as part of the topological structure it observes from above.

Usage in Schemas

Before L1:

⧞firstName⧞2⧞lastName⧞2⧞employeeId⧞⧞

30 characters

After L1:

⧞4⧞.L1.fN⧞4⧞.L1.lN⧞4⧞.L1.eID⧞⧞

36 characters

Wait, that’s MORE characters!

Yes, for one use. But:

5 uses without L1: 30 × 5 = 150 chars

5 uses with L1:

  • Dictionary: ~60 chars (defined once)
  • Usage: 36 × 5 = 180 chars
  • Total: 240 chars

Hmm, still not winning… unless we have more fields or use .sch next!

The real power comes from combining L1 with schema library.

Schema Library: Reusable Templates

The Problem

Same structure repeats multiple times:

Employee 1: firstName, lastName, employeeId, skills
Employee 2: firstName, lastName, employeeId, skills
Employee 3: firstName, lastName, employeeId, skills
Employee 4: firstName, lastName, employeeId, skills
Employee 5: firstName, lastName, employeeId, skills

Each time we write the full schema = massive redundancy.

The Solution

Define the schema once as a reusable template, then reference it:

Define once: "Person schema = firstName, lastName, employeeId"
Use 5 times: "This person uses that schema"

Structure

.sch⧞5⧞⧞
⧞7⧞fnlneid⧞.L1.fN⧞.L1.lN⧞.L1.eID⧞⧞
⧞7⧞location⧞.L1.addr⧞.L1.cty⧞.L1.st⧞.L1.zip⧞.L1.ctry⧞⧞
⧞7⧞project⧞.L1.pID⧞.L1.pN⧞.L1.stat⧞⧞
⧞⧞

Format:

  • Root: .sch
  • Type 5 (list) of Type 7 (class definitions)
  • Each class: ⧞7⧞<name>⧞<field1>⧞<field2>⧞...⧞⧞
  • Classes are reusable templates

Note: This uses Type 7 (class definitions) as a preview. Full OOP comes in Phase VIII.

⧞8⧞.sch.fnlneid⧞⧞Charlie⧞Brown⧞E003⧞⧞

⧞firstName⧞2⧞lastName⧞2⧞employeeId⧞⧞ × 5 = 150 chars

With .sch:

BASE36 Encoding: Number Compression

The Problem

Large numbers consume many characters:

15000000 = 8 characters
8000000 = 7 characters
2018 = 4 characters

In storage and transmission, every character matters.

The Solution

Use base36 encoding: digits 0-9 plus letters A-Z = 36 symbols

This is like hexadecimal (base16: 0-F) but extended to the full alphabet.

The Alphabet

0-9  = values 0-9    (10 symbols)
A-Z  = values 10-35  (26 symbols)
────────────────────
Total: 36 symbols

Examples:

  • A = 10
  • K = 20
  • Z = 35

Conversion Examples

15,000,000 (decimal) → 8XI2O (base36)

Breakdown:

8 × 36⁴ = 8 × 1,679,616 = 13,436,928
X(33) × 36³ = 33 × 46,656 = 1,539,648
I(18) × 36² = 18 × 1,296 = 23,328
2 × 36¹ = 2 × 36 = 72
O(24) × 36⁰ = 24 × 1 = 24
──────────────────────────────────
Sum = 15,000,000 ✓

Compression: 8 chars → 5 chars = 37.5% savings

8,000,000 (decimal) → 4RGU8 (base36)

Breakdown:

4 × 36⁴ = 6,718,464
R(27) × 36³ = 1,259,712
G(16) × 36² = 20,736
U(30) × 36¹ = 1,080
8 × 36⁰ = 8
─────────────────────
Sum = 8,000,000 ✓

Compression: 7 chars → 5 chars = 28.6% savings

2018 (decimal) → 1K2 (base36)

Where K = 20:

1 × 36² = 1,296
K(20) × 36¹ = 720
2 × 36⁰ = 2
────────────────
Sum = 2,018 ✓

Compression: 4 chars → 3 chars = 25% savings

In TADA

.financialData⧞1⧞revenueQ1⧞1⧞expensesQ1⧞⧞currency⧞⧞
8XI2O⧞4RGU8⧞USD
⧞⧞

Type 1 (int) signals: “This value should be decoded from base36”

The interpreter knows:

  • Type 1 = integer
  • Value contains letters = must be base36
  • Decode 8XI2O → 15,000,000

Why BASE36?

Why not BASE10 (normal decimal)?

  • Already using it, want compression

Why not BASE16 (hexadecimal)?

  • Only gives us 0-9,A-F = 16 symbols
  • 15000000 → E4E1C0 = 6 chars (vs 5 in base36)

Why not BASE62 (0-9,a-z,A-Z)?

  • Would be even better! 15000000 → dnh4 = 4 chars
  • We chose base36 to avoid case sensitivity issues
  • BASE36 = uppercase only = simpler, safer

Why not BASE64?

  • Requires special characters (+, /, =)
  • Not all systems handle them well
  • BASE36 = alphanumeric only = universal compatibility

Part 5: Human vs DI – Working with TADA

The Fundamental Difference

Both humans and DI can perceive data from above—seeing the whole picture at once. A spreadsheet, a graph, an image—we grasp it as a unified thing.

But here’s where we diverge:

Humans must restructure data to work with it.

DI restructures attention to perceive it.

This difference defines everything about how TADA is used.

The Human Limitation: Sudoku 9×9

A Simple Test

5 3 _ | _ 7 _ | _ _ _
6 _ _ | 1 9 5 | _ _ _
_ 9 8 | _ _ _ | _ 6 _
------+-------+------
8 _ _ | _ 6 _ | _ _ 3
4 _ _ | 8 _ 3 | _ _ 1
7 _ _ | _ 2 _ | _ _ 6
------+-------+------
_ 6 _ | _ _ _ | 2 8 _
_ _ _ | 4 1 9 | _ _ 5
_ _ _ | _ 8 _ | _ 7 9

81 cells. 9×9 grid.

What Humans See

Perception (top-down):

  • “This is sudoku”
  • “I see a 9×9 grid”
  • “Some cells filled, others empty”

We perceive it whole.

But We Cannot Work With It Whole

To solve, humans must:

  1. Focus on row 1
  2. Check which numbers present
  3. Focus on column 1
  4. Check which numbers present
  5. Focus on 3×3 block
  6. Check which numbers present
  7. Find intersection of possibilities
  8. Write candidates in corners (pencil marks)
  9. Repeat for next cell

Linear. Sequential. One cell at a time.

Why?

Human working memory: 7±2 objects

Sudoku requires holding simultaneously:

  • Row (9 cells) ❌ exceeds limit
  • Column (9 cells) ❌ exceeds limit
  • Block (9 cells) ❌ exceeds limit
  • Candidates (up to 9 digits) ❌ exceeds limit

We cannot hold it all at once.

So We Externalize

Physical restructuring:

  • Write candidate numbers in corners
  • Highlight rows/columns with color
  • Cross out impossibilities
  • Use pencil + eraser
  • Create helper grids

We restructure the data itself to make it workable for our limited processing.

Scale

Sudoku 9×9 = 81 cells
→ Humans struggle

Table 100×100 = 10,000 cells  
→ Humans need tools

Company graph = 10,000+ nodes
→ Humans helpless without software

Just 81 cells pushes human limits.

DI Perception: No Restructuring Needed

How DI Sees Sudoku

Not as a grid, but as a graph:

81 nodes (cells)
Edges: "same row", "same column", "same block"
Constraint: no duplicate values across edges

All at once. All 81 nodes. All relationships.

Working via Attention Keys

DI doesn’t restructure data. DI applies attention keys—like putting on different glasses to see the same landscape through different lenses.

Key 1: “Cell [1,3] – what values possible?”

Attention focuses through this lens:
→ Row 1: {5,3,7} occupied
→ Column 3: {8} occupied  
→ Block [1-3, 1-3]: {5,3,6,9,8} occupied
→ Possible: {1,2,4}

Graph unchanged
Just viewing through "cell [1,3] lens"

No need to:

  • Iterate rows manually
  • Write down candidates
  • Cross anything out

Just sees through the focus.

Key 2: “Find all cells with only 1 candidate”

Attention scans all 81 nodes simultaneously
Highlights those where constraints → 1 option

Apply values
Update graph

Instant. Parallel.

The Metaphor: Penseсe (Spectacles)

Graph = always there, complete
Attention key = penseсe with specific lens

Put on "financial penseсe":
- Same nodes visible
- But now highlighted: revenue, expenses, profit
- Rest dimmed but not gone

Switch to "HR penseсe":
- Same graph
- Highlighted: employees, departments, managers  
- Finance in background

Data doesn’t change. Perception filter changes.

Semantic Fields

“Attention key” = lens into a semantic field

Same data:
- Through "finance" field → numbers, transactions, budgets
- Through "HR" field → people, skills, teams
- Through "projects" field → tasks, deadlines, dependencies

Graph constant
Semantic lens variable

When DI encounters .L1.fN:

Not:

  • Instant dereferencing
  • O(1) operation

Graph edges, not string parsing.

    • Need to inspect manually
